# 上下文历史重建与菜单版本回溯设计

## 1. 目标

在保持现有 `POST /api/recommend` 请求兼容的前提下，补齐两项多轮交互能力：

1. 不带 `session_id` 但提交完整消息历史时，系统能够按轮次重建之前的菜单，再应用最后一轮约束。
2. 带有 `session_id` 时，系统保存每次推荐的菜单版本，并支持恢复到指定版本或撤销上一轮修改。

实现必须离线运行，不引入外部模型、数据库或网络依赖，并且不能破坏现有的过敏、忌口、营养和最小修改规则。

## 2. 当前问题

当前 `SessionStore` 只保存一个会话的最新菜单、最新约束和最新消息。它可以支持继续对话，但无法：

- 查看历史菜单版本；
- 恢复到第 N 版；
- 在没有 `session_id` 时按完整历史重放上一轮菜单；
- 在回滚后继续基于恢复的菜单进行增量修改。

## 3. 方案

### 3.1 会话版本快照

为每个会话增加 `MenuSnapshot`，保存：

- `version`：从 1 开始递增的菜单版本号；
- `messages`：生成该版本时的完整消息历史；
- `menu_ids`：官方菜谱 ID 列表；
- `constraints`：结构化约束快照；
- `operation`：`recommendation` 或 `rollback`；
- `source_version`：回滚版本的来源版本；
- `created_at`：创建时间。

`SessionState` 继续暴露最新版本字段，保证现有调用方兼容，同时增加有限长度的历史列表。历史最多保留 32 个版本，会话仍按现有 TTL 和最大会话数清理。

### 3.2 完整历史重建

当请求没有有效 `session_id` 时：

- 将 `messages` 视为按时间顺序排列的完整历史；
- 从第一条消息开始逐轮调用现有规划器；
- 每一轮使用上一轮菜单 ID 作为 `previous_menu_ids`；
- 最终保存每轮快照，并返回最后一轮结果。

当请求带有有效 `session_id` 且 `messages` 以已保存历史为前缀时，只处理新增后缀消息，避免重复生成版本。

### 3.3 回滚行为

支持两种入口：

- API 请求体增加可选字段 `rollback_to`，值为目标版本号；
- 自然语言识别：
  - “撤销刚才修改”“恢复上一版”回到当前版本的前一版；
  - “回到第 1 版”“恢复到 v2”回到指定版本。

回滚不会删除历史。系统会复制目标版本的内容，创建一个新的当前版本。例如当前为 v3，回到 v1 后生成 v4，v4 的 `source_version` 为 1。后续对话基于 v4 继续。

目标版本不存在时返回明确的 400 错误，不静默生成新菜单。

### 3.4 API 输出

推荐接口在现有响应基础上增加：

- `menu_version`：当前菜单版本；
- `history`：历史版本摘要；
- `changes.mode`：`new_menu`、`minimal_revision` 或 `rollback`；
- 回滚时增加 `changes.from_version`、`changes.to_version`、`changes.source_version`。

增加只读接口：

```text
GET /api/sessions/{session_id}/history
```

该接口只返回版本摘要，不暴露会话内部实现细节。

## 4. 测试范围

必须覆盖：

- 多轮请求不带 `session_id` 时，完整历史重建结果与逐轮带 `session_id` 结果一致；
- `rollback_to` 能恢复指定版本；
- “撤销刚才修改”能恢复前一版本；
- 回滚后追加新的忌口只替换必要菜品；
- 版本历史按顺序递增，回滚不删除旧版本；
- 无效版本返回 400；
- 历史查询接口返回版本摘要；
- 现有单轮、多轮、自动批测和网页烟测继续通过。

## 5. 非目标

- 不实现跨进程持久化数据库；
- 不实现用户账号级长期历史；
- 不修改官方评分算法；
- 不允许通过回滚绕过过敏和明确忌口校验；
- 不引入在线大模型或在线 API。
