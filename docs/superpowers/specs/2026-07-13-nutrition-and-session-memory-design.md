# 精确营养评估与最小修改会话记忆设计

## 1. 目标

在保持现有 `POST /api/recommend` 向后兼容的前提下，完成三项能力：

1. 用可追溯的权威食物成分数据、菜谱实际用量和烹饪修正，估算每道菜、整桌及每位用户的营养摄入。
2. 通过会话状态或完整对话历史保存上一轮菜单，只替换违反新增约束的最少菜品。
3. 建立自动评委测试和组合压力测试，持续发现硬约束、搭配、营养、多轮修改及性能问题。

系统输出属于膳食营养估算，不宣称达到实验室检测或临床诊断精度。任何缺失数据、默认用量和估算误差都必须体现在覆盖率、可信等级和误差说明中。

## 2. 设计原则

- 过敏、明确忌口和特殊人群禁忌是硬约束，优先级高于营养分和用户偏好。
- 推荐菜品只能来自官方菜谱库，营养计算不得改变这一真实性要求。
- 营养结果必须可追溯到食材、重量、数据条目及修正规则，不能按标签伪造精确数值。
- 评测运行期间不依赖外网或 API 密钥，营养数据子集随 Docker 镜像离线加载。
- 新增条件默认执行最小修改；只有明确要求全部重做时才放弃上一轮菜单。
- `session_id` 是可选增强。只提供现有 `user_id + messages` 的评测请求仍须正常工作。
- 低可信结果不能标记为精确达标，必须显示为估算并列出主要误差来源。

## 3. 总体架构与数据流

推荐链路调整为：

```text
请求标准化
  -> 会话/完整历史恢复
  -> 约束抽取与冲突检测
  -> 官方菜谱硬约束过滤
  -> 食材解析与营养估算
  -> 候选菜排序
  -> 上一轮菜单逐道校验与锁定
  -> 最少替换和整桌营养优化
  -> 结果审计
  -> 会话快照更新与 API 响应
```

新增模块边界：

- `app/ingredient_parser.py`：将食材清单解析为标准名称、数量、单位和原始文本。
- `app/nutrition_repository.py`：加载离线营养数据、名称别名和数据来源。
- `app/nutrition_calculator.py`：计算单食材、单菜、整桌和人均营养。
- `app/nutrition_targets.py`：根据人群、健康目标和餐次生成目标区间。
- `app/nutrition_scoring.py`：计算营养分项、总体均衡度和可信度。
- `app/session_store.py`：管理有上限、可过期且线程安全的内存会话。
- `app/menu_revision.py`：校验旧菜单、锁定可保留项并执行最少替换。
- `app/history_replay.py`：在没有 `session_id` 时按完整消息历史重建前一轮结果。
- `tests/judge_cases/`：保存固定回归、组合约束和性能场景。

现有 `constraints.py`、`retriever.py`、`planner.py` 和 `agent.py` 继续负责原有边界，通过新增模块组合能力，不把营养解析和会话状态继续堆进单个文件。

## 4. 营养数据与可追溯性

### 4.1 数据来源

第一版采用可合法再分发的 USDA FoodData Central 基础食物条目作为权威来源，并保存来源名称、条目 ID、版本和每 100 克营养值。构建阶段扫描 2000 道菜谱中的标准食材，仅打包实际使用的离线子集。

若后续获得《中国食物成分表》的合法电子数据，则中文本土食材优先使用该来源，USDA 作为补充。不同来源不能静默混用；每个匹配项保留其来源标识。

离线数据至少包含：

- 能量 `kcal`
- 蛋白质 `protein_g`
- 脂肪 `fat_g`
- 碳水化合物 `carbohydrate_g`
- 膳食纤维 `fiber_g`
- 糖 `sugar_g`
- 钠 `sodium_mg`

### 4.2 中文名称匹配

食材标准化分为精确名称、人工审核别名和受控模糊匹配三级。比如“西红柿/番茄”和“生抽/酱油”映射到稳定的标准条目。模糊匹配只能在置信阈值以上使用，并记录候选和得分；不能把低分候选当成确定结果。

食材映射表必须经过覆盖率报告审查。高频且未匹配的食材优先人工补齐，避免通过扩大模糊匹配范围换取虚假覆盖率。

### 4.3 数据许可证

营养数据、别名表和派生子集必须在 `data/nutrition/README.md` 记录来源 URL、下载日期、版本、许可证和生成方式。只有许可证允许再分发的数据进入仓库或 Docker 镜像；否则只提交可重复构建脚本和说明。

## 5. 食材用量解析

解析器输出统一结构：

```json
{
  "raw_name": "鸡胸肉",
  "canonical_name": "鸡胸肉（去皮，生）",
  "amount": 200,
  "unit": "g",
  "grams": 200,
  "amount_source": "explicit",
  "match_source": "alias",
  "confidence": 0.96
}
```

用量优先级：

1. 明确质量：`200g`、`1.5kg`。
2. 明确体积：`250ml`，使用对应食材密度换算。
3. 常见量具和自然单位：`1勺`、`半碗`、`2个鸡蛋`，使用版本化标准重量表。
4. `少许、适量`：使用食材类别的保守默认量并降低可信度。
5. 无法识别：保留为缺失食材，不计入已知营养总量，不擅自填充。

括号中的预处理状态需要保留，例如“去皮”“泡发”“熟重”。营养条目优先匹配同状态数据；无法匹配时使用最接近条目并记录误差来源。

调味料不能因用量小而忽略。盐、酱油、糖、食用油对钠、糖和脂肪评分有直接影响。对“适量盐”等表达采用可配置默认值，但在高血压场景中使用保守上界进行风险判断。

## 6. 份数推定与营养计算

### 6.1 份数

菜谱缺少统一份数时，系统根据可食食材总重量、菜品类别和标准单人份重量推定份数：

```text
estimated_servings = edible_weight / category_portion_weight
```

推定结果限制在合理范围，并输出区间而非不必要的精确小数。用户提供就餐人数时，整桌总量按实际人数折算；没有提供人数时使用推定份数。

### 6.2 单食材和单菜计算

明确重量食材按以下公式计算：

```text
nutrient = grams / 100 * nutrient_per_100g * retention_factor
```

烹饪修正只用于有可靠依据且受影响明显的营养素。油炸吸油、焯水钠损失等单独建模；不存在可靠参数时不虚构修正，并在误差说明中标记。

### 6.3 整桌和个人摄入

系统先汇总所有菜品得到整桌总量，再根据人数和默认等份原则计算每人摄入。多人档案存在时，对每个人分别应用营养目标和健康限制；不能用一个平均用户代表全桌。

第一版默认等份分配。若对话明确说明儿童少吃、某人不吃某道菜等份量关系，则使用个人分配系数。无法确认时主动说明等份假设。

## 7. 营养目标与整桌均衡评分

目标区间由年龄、性别、特殊人群、健康目标、餐次和就餐人数共同决定。没有足够个人信息时采用一般成人餐次参考区间并标注假设，不生成医学化建议。

整桌评分至少包含：

- 能量是否落在餐次目标区间；
- 蛋白质总量及供能比；
- 脂肪和碳水供能比；
- 膳食纤维是否充足；
- 钠是否超限；
- 添加糖风险；
- 荤素、主食、汤类及烹饪方式多样性。

硬约束和软评分分离：过敏违反直接淘汰，不能通过其他高分抵消。高血压、控糖等场景对钠和糖使用更严格阈值。结果按个人返回各自分项判断，并给出整桌总体分数。

可信度由以下因素共同决定：

- 营养数据库匹配覆盖率；
- 明确重量覆盖率；
- 默认用量占比；
- 食材状态匹配质量；
- 份数是否由用户明确提供；
- 烹饪修正依据完整性。

输出 `high`、`medium`、`low` 三级，同时保留 0 到 1 的内部得分。低可信度菜单只能显示“估算基本合理”或“数据不足”，不能显示“精确达标”。

## 8. 会话与最小修改

### 8.1 会话状态

首次请求创建随机不可预测的 `session_id`，保存：

- 累积消息和解析后的约束；
- 当前菜单及每道菜营养摘要；
- 菜单版本号；
- 用户档案 ID 或对话推断档案；
- 创建时间和最后访问时间。

会话只存于进程内存，不写入磁盘，默认两小时过期，并设置最大会话数。访问会刷新最后使用时间，淘汰采用过期优先和最久未使用策略。每个会话更新使用锁，防止并发覆盖。

### 8.2 双模式恢复

模式 A：请求携带有效 `session_id` 时，只需提交新增消息，系统从会话快照恢复上一轮菜单。

模式 B：不携带 `session_id` 但提供完整 `messages` 时，将最后一条视作新增轮次，用前面的历史确定前一轮约束和菜单，再应用最后一轮修改。为保证重放稳定，候选排序必须使用确定性次序，分数相同按菜谱 ID 排序。

若 `session_id` 失效但请求包含足够完整历史，自动回退模式 B。若两者都不足，则作为新会话生成菜单，不返回服务器错误。

### 8.3 修改算法

1. 合并新增约束，识别局部修改、全部重做和模糊表达。
2. 对上一轮每道菜重新执行硬约束、显式指令和营养检查。
3. 无冲突菜品锁定保留；违反新增硬约束或被用户点名的菜进入替换集合。
4. 替换候选优先保持原菜类别、主要营养作用和烹饪方式。
5. 组合新整桌并重新计算每个人的营养。若整桌因局部替换失衡，搜索增加最少联动替换的方案。
6. 在满足所有硬约束的方案中，先最小化替换数量，再优化营养和搭配分。

优化优先级定义为：

```text
硬约束零违反
  > 用户明确局部指令
  > 替换数量最少
  > 个人营养安全
  > 整桌营养均衡
  > 偏好和多样性
```

“不要虾，其他菜保留”通常只替换含虾菜。若新增“高血压，整桌低钠”使两道菜超限，则允许替换两道，并解释这是满足新增健康约束所需的最少联动修改。

识别到“全部换掉、重新推荐、换一桌”等明确表达时取消菜单锁定。模糊要求无法安全判断时，返回澄清问题，不盲目修改。

### 8.4 可验证修改记录

返回结果包含：

```json
{
  "changes": {
    "mode": "minimal_revision",
    "kept_dishes": [101, 205, 330],
    "replaced_dishes": [
      {"old_id": 88, "new_id": 412, "reason": "新增虾过敏约束"}
    ],
    "change_count": 1
  }
}
```

`minimal_change` 不能再固定为 `true`。它由审计器验证：是否存在满足相同硬约束且替换数更少的可行方案。

## 9. API 契约与兼容性

原请求继续支持：

```json
{
  "user_id": 3,
  "messages": ["推荐4道晚餐"]
}
```

增强请求支持：

```json
{
  "user_id": 3,
  "session_id": "可选",
  "message": "不要虾，其他菜保留"
}
```

原有 `menu`、`constraints`、`score_card`、`warnings` 和 `answer` 字段保持。新增：

- `nutrition`：每道菜、整桌和人均营养；
- `nutrition_score`：分项与整桌均衡评分；
- `confidence`：覆盖率、可信等级、缺失食材和误差来源；
- `session_id` 和 `menu_version`；
- `changes`：保留、替换及原因。

无 `session_id` 的现有客户端无须修改。前端增强后保存服务器返回的会话 ID，但不能把浏览器状态作为唯一会话来源。

## 10. 错误处理与降级

- 营养条目缺失：保留菜谱候选，列入 `missing_ingredients` 并降低可信度。
- 用量无法解析：不编造明确克数；按规则默认时必须记录默认来源。
- 全部候选违反硬约束：返回空菜单、冲突说明和建议澄清项，禁止返回“最接近但违规”的菜。
- 营养优化无完全达标方案：选择硬约束全部满足且偏差最小的方案，列出未达标项。
- 会话过期：使用完整历史重放；没有历史时创建新会话。
- 并发版本冲突：客户端可提交 `menu_version`；版本落后时返回当前版本和可重试提示，避免静默覆盖。
- 营养数据文件损坏：健康检查报告不可用，推荐接口可按原规则降级，但必须明确 `nutrition_status: unavailable`。

## 11. 自动评委测试与 Bug 发现

测试分四层：

1. 单元测试：中文单位、数量、别名、营养公式、份数和置信度。
2. 回归测试：保存已发现的海蛎子、辣味、甜味、菜品数量和早餐问题。
3. 组合测试：程序化组合过敏、忌口、疾病、偏好、人数、餐次和菜品数量，校验不变量。
4. API 场景测试：完整历史、有效会话、过期会话、局部替换、全部重做、并发版本和响应时间。

自动审计不变量：

- 推荐菜谱 ID 和内容必须来自官方库；
- 已识别过敏与明确忌口违反数为零；
- 菜品数量符合明确要求；
- 菜单没有重复菜；
- 营养汇总等于各食材、各菜的可解释加总；
- 人均总量与人数折算一致；
- 低可信度不得标记精确达标；
- 单一新增冲突通常只替换一道菜；
- 无冲突追加要求不改变原菜单；
- 完整历史模式与会话模式产生相同的修改结果；
- 推荐核心计算目标低于两秒，营养数据只在启动时加载一次。

组合测试使用固定随机种子保证可复现。失败报告保存输入、约束、菜单、违反规则、营养差异、修改记录和耗时，让开发者无需人工逐条对话即可定位问题。

## 12. 验收标准

- 官方菜谱真实性：100%。
- 已识别过敏与忌口违反数：0。
- 明确重量营养公式与基准计算差异：不超过 5%。
- 已纳入标准单位和别名测试集的解析正确率：不低于 95%。
- 菜谱食材营养数据覆盖率目标：不低于 85%；低覆盖结果必须显式标记。
- 单个新增菜品冲突且存在同类候选时：仅替换冲突菜。
- 无新增冲突时：原菜单 ID 顺序保持不变。
- 完整历史模式与会话模式：相同输入语义下菜单与修改记录一致。
- 推荐核心计算：单轮目标低于 2 秒，并记录 P50、P95 和最慢场景。

这里的 5% 指软件公式和基准数据的计算一致性，不代表菜品实际化验值误差。菜谱原始用量、可食部和烹饪吸收的不确定性统一由可信度表达。

## 13. 不在本阶段范围内

- 医疗诊断、疾病治疗方案或药物相互作用建议；
- 实验室级营养检测精度承诺；
- 用户长期健康档案持久化；
- 依赖在线大模型或在线营养 API 才能完成的核心推荐；
- 第一版支持任意复杂的个人分餐比例优化。
