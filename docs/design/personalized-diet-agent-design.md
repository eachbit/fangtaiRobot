# 个性化膳食规划 Agent 设计方案

## 1. 项目定位

项目名称暂定为“健康约束可验证的个性化膳食规划 Agent”。

项目面向方太人工智能专项赛的个性化膳食规划 Agent 赛道。系统不直接让大模型自由生成菜单，而是采用“官方菜谱库检索 + 用户健康档案约束 + 规则校验 + 大模型自然语言解释”的方式，生成可验证、可追溯、可解释的膳食推荐结果。

核心目标是先做出稳定可提交版本，再在此基础上扩展创新展示能力。

## 2. 已知数据

系统使用三类官方数据：

- `recipes_sample_2000.csv`
  - 编码：GBK
  - 字段：`名称`、`食材清单`、`烹饪步骤`、`label`
  - 用途：官方菜谱库，所有推荐菜品必须来自该文件，避免幻觉生成。
- `50个用户健康档案（脱敏）.json`
  - 字段：`id`、`性别`、`年龄`、`劳动强度`、`特殊人群`、`孕周期`、`口味偏好`、`过敏食材`、`健康需求`
  - 用途：用户约束来源。
- `对话用例.json`
  - 20 组测试用例
  - 覆盖单轮、多轮、追加约束、多人偏好冲突、时间限制等场景。

## 3. 评分导向

系统设计对应评分项：

- 基础推荐：保证忌口、过敏、菜谱真实性。
- 复杂场景组合：支持多人、多约束、餐别、口味、健康目标的综合推荐。
- 多轮动态交互：保留上下文，用户追加约束时尽量只修改必要部分。
- 性能效率：优先使用本地检索和规则校验，降低每轮响应耗时。

## 4. MVP 范围

第一版必须完成：

- 读取官方菜谱 CSV 和健康档案 JSON。
- 提供后端 API。
- 提供网页演示界面。
- 支持选择用户档案。
- 支持输入单轮或多轮对话。
- 抽取基础约束：
  - 餐别
  - 人数
  - 口味偏好
  - 过敏食材
  - 健康需求
  - 时间/复杂度倾向
  - 食材限制
- 从官方菜谱库检索候选菜。
- 对候选菜做约束校验。
- 输出推荐菜单、推荐理由、风险提示和约束评分卡。

第一版不做：

- 医疗级营养诊断。
- 精确营养素计算。
- 长期用户画像学习。
- 复杂多日膳食计划。
- 大规模模型训练。

## 5. 创新点

主要创新点是“约束评分卡”。

每次推荐结果不仅给出菜单，还输出一张结构化评分卡：

- 菜谱真实性：是否来自官方菜谱库。
- 过敏风险：是否命中过敏食材。
- 健康适配：是否匹配健康需求。
- 口味适配：是否符合用户口味或对话偏好。
- 场景适配：是否符合餐别、人数、时间限制。
- 修改幅度：多轮对话中是否遵守最小修改原则。

该创新点适合答辩表达，且能直接支撑系统可靠性说明。

## 6. 系统架构

系统由三层组成：

1. 网页演示界面
   - 面向评委、老师和答辩展示。
   - 调用后端 API。
   - 展示用户档案、对话输入、推荐菜单、约束解析、校验结果和评分卡。

2. 后端 API
   - 面向官方测评和网页调用。
   - 提供统一接口，避免网页和测评使用两套逻辑。

3. 膳食规划核心模块
   - 负责数据加载、约束抽取、菜谱检索、健康校验、菜单组合和结果生成。

## 7. 后端模块

后端建议拆分为以下模块：

- `data_loader`
  - 读取菜谱 CSV。
  - 读取用户健康档案 JSON。
  - 处理 GBK 编码。

- `constraint_extractor`
  - 从用户多轮消息中抽取结构化约束。
  - 将“清爽一点”“别太复杂”“减脂”“两个人”等自然语言转为可计算字段。

- `recipe_retriever`
  - 基于菜名、食材、标签、餐别、口味、健康需求检索候选菜。
  - 候选菜必须来自官方菜谱库。

- `health_checker`
  - 校验过敏食材。
  - 校验特殊人群风险。
  - 校验健康需求和菜谱标签的匹配程度。

- `meal_planner`
  - 从候选菜中组合一餐菜单。
  - 平衡主食、荤菜、素菜、汤/小菜。
  - 支持一人、两人、家庭、多人聚餐等场景。

- `dialog_manager`
  - 管理多轮对话状态。
  - 用户追加约束时保留已有计划，优先最小修改。

- `response_generator`
  - 生成自然语言回答。
  - 输出推荐理由、注意事项和替代方案。

- `scoring_card`
  - 生成约束评分卡。
  - 给网页和 API 同时使用。

## 8. API 设计

核心接口：

`POST /api/recommend`

请求示例：

```json
{
  "user_id": 3,
  "messages": [
    "中午这顿饭你帮我安排一下。",
    "两个人吃，最近在减脂。"
  ]
}
```

响应示例：

```json
{
  "user_id": 3,
  "constraints": {
    "meal": "午餐",
    "people_count": 2,
    "taste": "清淡",
    "health_goals": ["减脂"],
    "allergens": ["花生"]
  },
  "menu": [
    {
      "name": "蔬菜焗蝴蝶面",
      "ingredients": "A料：蝴蝶面300克；西葫芦150克...",
      "labels": ["早餐", "下午茶", "清淡", "减脂"],
      "reason": "该菜来自官方菜谱库，标签包含清淡和减脂，适合当前用户的午餐需求。"
    }
  ],
  "score_card": {
    "official_recipe": true,
    "allergy_passed": true,
    "health_match": "medium",
    "taste_match": "high",
    "scenario_match": "high",
    "minimal_change": true
  },
  "warnings": [],
  "answer": "建议安排蔬菜焗蝴蝶面，整体口味清淡，适合减脂场景。"
}
```

辅助接口：

- `GET /api/users`
  - 返回用户档案列表。
- `GET /api/recipes`
  - 返回菜谱检索结果，供调试和演示使用。
- `GET /api/health`
  - 返回服务状态。

## 9. 网页演示界面

网页第一版包含：

- 用户选择区
  - 选择 50 个用户档案之一。
  - 展示用户基础信息、过敏食材、健康需求。

- 对话输入区
  - 支持输入多轮消息。
  - 支持一键加载官方 20 个对话用例。

- 推荐结果区
  - 展示推荐菜单。
  - 展示每道菜的食材、标签和推荐理由。

- 约束解析区
  - 展示系统从对话和健康档案中抽取到的约束。

- 评分卡区
  - 展示菜谱真实性、过敏风险、健康适配、口味适配、场景适配。

- 风险提示区
  - 展示过敏、特殊人群、冲突需求等提示。

## 10. 多轮对话策略

系统保留当前会话状态：

- 用户第一轮提出泛需求时，生成初始推荐。
- 用户追加“别辣”“十分钟内”“两个人”“减脂”等约束时，更新约束集合。
- 原推荐中仍满足新约束的菜尽量保留。
- 只替换违反新约束的菜。

该策略用于支撑“上下文一致性”和“最小化修改原则”。

## 11. 错误处理

必须处理：

- 用户 ID 不存在。
- 菜谱文件缺失或编码错误。
- 对话为空。
- 检索不到完全满足条件的菜。
- 用户健康档案包含多个冲突需求。

当无法完全满足约束时，系统返回降级结果：

- 明确说明哪些约束未完全满足。
- 给出最接近的替代方案。
- 不生成官方菜谱库之外的菜名。

## 12. 测试策略

第一阶段测试：

- 数据加载测试：确认 2000 条菜谱和 50 个用户档案可读取。
- API 测试：确认 `/api/recommend` 能返回稳定 JSON。
- 约束抽取测试：覆盖 20 个官方对话用例。
- 过敏校验测试：构造海鲜、花生、鸡蛋、牛奶等过敏场景。
- 多轮测试：验证追加约束后是否最小修改。
- 性能测试：记录单轮端到端响应耗时。

## 14. 后续扩展路线

核心版完成后可扩展：

- 多人多约束冲突调和。
- 推荐方案对比：清淡版、快手版、高蛋白版。
- 更细的疾病/特殊人群饮食规则。
- 简单营养估算。
- 可视化推荐路径。
- Docker 镜像部署。

扩展原则：不破坏核心 API，不重写推荐主流程。

## 15. 当前决策

当前确认：

- 采用 API + 网页演示界面。
- 采用稳分优先方案。
- 创新点集中在约束评分卡和可验证推荐链路。
- 第一版目标是可提交、可演示、可解释。
